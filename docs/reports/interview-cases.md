# AgentLens 面试案例库：设计与验证方式

> 用法：每个案例按「约束 → 首次尝试与翻车数据 → 根因 → 修复 → 修复后数据 → 面试叙事点」组织。
> 已完成案例含真实数据与 commit 号；规划中案例列出验证设计与**待采集数字**——实现时必须把
> before/after 数据回填进来，没有数字的案例在面试里站不住。
>
> 面试叙事总原则（来自外部实践的两条铁律）：
> 1. **翻车数据比成功数据值钱**——"96% 准确率实为随机"的故事永远比"我们做到了 95%"可信；
> 2. **评估器本身也要被评估**——任何"通过率 X%"都要能回答"这个 X 凭什么可信"。

## A. 已完成案例（真实数据）

### A1. JVM 链接期验证击穿 CI 冒烟：手拼 classpath 的隐藏契约

- **约束**：CI 的 demo 步骤用 4 模块手拼 classpath 直接启动主类，历来"能跑"。
- **翻车**：CI 报 `NoClassDefFoundError: DshAgentAdapter$LiveListener`——缺的类**根本不在**
  demo 的执行路径上（demo 只用 mock 适配器，不碰 DSH live 模式）。
- **根因**：JVM **链接期**验证主类时，必须把方法体中匿名类解析到它实现的接口
  （`dshLiveRun` 的 `new LiveListener(){...}`）；验证发生在 `main` 执行前，与运行路径无关。
  用 `-Xlog:class+load` 抓到加载链：ConfigException → RunExistsException → Evaluator →
  死在 LiveListener——每一步都是验证器按 catch 类型/帧类型逐个解析的证据。
- **修复**：步骤改走 `mvn exec:java`（从 install 过的 reactor 构件解析完整运行时 classpath）。
- **验证**：本机用同款 4 模块 classpath 精确复现 → 修复后通过；类加载日志给出完整证据链。
- **面试叙事点**：类加载/链接/验证三阶段的边界（验证在链接期、执行在前）；"代码不执行的
  路径也会让类加载失败"这个反直觉点；CI 可观测性工具（`-Xlog:class+load`）。
  可追问：为什么参数类型 `DshAgentAdapter dsh` 没触发而匿名类接口触发了？——验证器对
  未解析类型可乐观延迟，但对栈帧中 `new` 目标与构造器属主的 assignability 检查需要解析。
- **证据**：commit `fbc32f6`；诊断输出留存在会话（加载链 4 行）。

### A2. 空白名单语义缺陷：一个"永远失败"的评测器分支

- **约束**：demo 确定性输出 `passed=false`，但 mock run 是 SUCCESS + 标准答案，理论全过。
- **定位**：单文件 Java 探针逐评测器打印 → `tool-policy passed=false unknown=[query_prometheus]`
  ——**没有声明 allowedTools 时，任何被调工具都判 unknown**。
- **根因**：代码里 `if (!allowedSet.isEmpty()) { unknown.removeAll(...) }` 的守卫本意是
  "空白名单跳过 unknown 剔除"，但剔除被跳过后 unknown 仍计入失败——守卫只做了一半。
- **修复**：空白名单 → unknown 检查不适用（与 compliance 评测器"未声明=不可验证"哲学对齐）；
  forbidden 集在任何情况下照常强制。+2 测试锁语义。
- **验证**：探针逐评测器 before/after；demo 恢复 `passed=true`；白名单非空路径行为不变
  （既有测试零改动通过）。
- **面试叙事点**：半截守卫（guard 只保护了计算、没保护判定）；语义设计要回答"缺省值
  是严格还是豁免"并全库对齐；定位方法论——不要读代码猜，写探针拿事实。
- **证据**：commit `968b80e`。

### A3. 断言代数上线即全灭：0.000 的 pass^k 与三层根因

- **约束**：断言代数（`not-`/权重/k-of-n）接入 run 路径后，CI 冒烟语料 20 场景
  `avgPassRate=0.000` 全灭——而其中 19 个场景的 mock 行为是 `correct`。
- **根因链（三层，逐层剥）**：
  1. 语料声明是**语义标签**（`identify_root_cause`，snake_case），断言匹配是**字面 contains**
     → 自然语言答案永远不含下划线串；
  2. 即便归一化下划线，`identify root cause`（声明语序）≠ `Root cause identified`（答案语序）
     ——contains 是语序敏感的；
  3. CI 步骤用旧退出码期望 `|| test $? -eq 1` 拦截了按契约属于 quality regression 的
     exit 100——修好了评测还有门在拦。
- **修复**：匹配侧做 identifier 归一（小写、`_`/`-`→空格、折叠空白，双侧归一）；
  语料改写为可执行字面形态 `["root cause identified", "w2:evidence", "not-<forbidden0>"]`
  （正向按答案语序、复用每场景 forbidden 工具做负向检查）；CI 期望对齐 exit 100 契约。
- **验证（分层闭环）**：单场景 `run` + `show --run` 逐评测器行定位到 success-assertions；
  修复后 20 场景 19 STABLE_PASS + 1 STABLE_FAIL（wrong_tool 按设计失败），
  `pass^k=0.950`；compare correct/correct exit 0、flaky 契约码 100。
- **面试叙事点**：**新能力开启后如何系统性验证存量兼容**（golden corpus 回归是被动的，
  主动做法是"语料可判定性静态检查"——声明能否被任何合理答案满足，可以在落盘时验证，
  这是我们事后补的教训）；字面断言 vs 语义断言的边界；归一化该做在哪一侧
  （两侧都做，声明侧负责 identifier 习惯、答案侧负责排版噪声）。
- **证据**：commits `5c4dea9` + `7aea64c`；修复前后 pass^k 0.000 → 0.950。

### A4. 存储层性能悬崖：一次冒烟卡死引出的 1500 倍修复（S3 期间发现）

- **约束**：S3 统计门禁冒烟 compare 反复卡死（2 分钟+ 无输出），而同期
  diagnose-calibrate 等命令 0.4 秒完成。
- **定位链（每步一个事实）**：jstack → main 在 ExperimentRunner.join 等 worker，
  全部 worker BLOCKED 在 `SqliteRunStore.saveRun` 的对象锁；持锁者 RUNNABLE 在
  SQLite JNI `step` 且 CPU 占用极低（11 秒 109ms）→ 不是计算慢，是 IO 等待；
  micro-probe 定量：单次 saveRun（3 事件的微型 run）**600ms**，且**空库同样慢**
  ——排除 754 案例数据量因素，锁定每语句 fsync（默认 journal+autocommit）
  × 慢速盘 IO。
- **修复**：WAL + synchronous=NORMAL + saveRun/saveEvaluation 显式单事务
  （autocommit 下每个 INSERT 独立 fsync）。
- **验证**：micro-probe before/after：**600ms → 0.3-0.7ms（约 1500 倍）**；
  200-run compare 全程 2 分钟+ → **4.3 秒**；质量门全绿，WAL 崩溃恢复语义
  保持（证据链安全性不降级）。
- **面试叙事点**：性能问题定位方法论（栈采样 → 锁竞争图 → 微基准定量 →
  对照实验排除变量——"空库也慢"一锤定音）；"评测基础设施自身的写入吞吐
  也是可信度的一部分"；修复不牺牲崩溃安全（WAL 恢复语义）。

## B. 规划中案例（验证设计已定，数字待实现时回填）

> 每项先写"验证方式"再写代码——面试时能讲清"我怎么知道它有效"的设计本身也是案例。
> 来源：淘天《可评可控可迭代》与电商《LLM-as-Judge 日级工业化》两篇实践的裁剪移植
> （原始数字 96%→50% 位置偏差、一致率 80% 但准确率 55%、86%→68%→55% 过拟合衰减，
> 可作为对比锚点在面试中引用）。

### B1. Pairwise 评审的位置偏差消解（对应 `compare --review`）

- **设计**：`compare --review` 让 LLM 对 baseline/candidate 两版输出做偏好评审。
  引入 (a) A/B 位置随机化；(b) 可选双向评估（正序+逆序各跑、取一致）。
- **验证方式**：固定评审集 × 两种位置安排，对比"固定位置 vs 随机 vs 双向取一致"的
  自一致率与对已知答案的准确率。**待采集数字**：固定位置的"虚假一致率"（预期虚高，
  参照外部 96%→50% 现象）、随机化后回落值、双向取一致的准确率增益与 3× 成本。
- **面试叙事点**：复现了业界系统性陷阱并用最简干预（随机化）拿回真实信号；
  成本-可信度的权衡曲线。

### B2. Judge Prompt 硬化：幻觉压制四件套

- **设计**：judge prompt 增加（a）锚定事实来源（仅基于输入判定）；（b）反向验证
  （先摘录 trace 原文片段作证据再下结论）；（c）禁止推断性判断——证据不足输出
  `insufficient_evidence` 显式判定而非硬判 0/1（与 fail-open 语义对齐）；(d) temperature 显式 0.1。
- **验证方式**：构造"证据不足"bad case 集（trace 被截断、工具返回缺失的 run），
  对比硬化前后：误判率（把不可评判成 fail）、`insufficient_evidence` 触发率、
  同输入 5 次重跑的判定一致率。**待采集数字**：误判率 before/after、一致率 before/after。
- **面试叙事点**："诚实跳过优于强行评分"——评测器的 N/A 是特性不是缺陷；
  prompt 改动的可测量验证而非"感觉变稳了"。

### B3. `--judge-votes N` 多轮投票与一致性置信过滤

- **设计**：judge 判定可选跑 N 次（temperature>0），3 轮一致=高置信、不一致=low-confidence，
  置信度进入 `EvaluationResult`/scores API/看板（衔接分数三来源模型）。
- **验证方式**：在标定语料上跑 3 轮投票，画"全体准确率 vs 3 轮一致子集准确率"
  对比曲线。**待采集数字**：一致子集占比、一致子集准确率 vs 全体准确率的差
  （外部参照：一致时 100% vs 全体 55%）。若差值不显著，如实记录并降级该特性——
  负结果也是案例。
- **面试叙事点**：一致性作为免费置信度过滤器的成立条件；"如果数据不支持设计预期怎么办"
  （如实报告、特性降级）。

### B4. 标定框架升级：语料分层 + 泛化 gap 监控

- **设计**：judge-calibration 语料从 10 条扩为分层结构（常规/边界/对抗/安全，比例由
  风险决定）；标定报告增加 train/validation 分割，报告泛化 gap；附样本量 CI 提示
  （±1pp 需多少样本）。judge prompt/模型版本指纹写入 approved-baseline，漂移即警告。
- **验证方式**：故意构造一条过拟合 rubric（只在特定样例上成立），展示 train 准确率
  与 validation 准确率的 gap 暴露它。**待采集数字**：正常 rubric 的 gap（预期 <5pp）、
  过拟合 rubric 的 gap（预期 >20pp）、样本量-CI 宽度对照表。
- **面试叙事点**：**评估器的过拟合是可以主动制造的、因此也是可以监控的**；
  "judge 版本变更比 prompt 变更更容易被忽视，却影响所有评测结论"。

### B5. 失败四层归因：先剥离评测体系自身的问题

- **设计**：失败 run 聚类的簇标签采用四层归因——**数据层**（导入轨迹脏数据：工具返回
  夹带系统提示词等）/ **规则层**（断言/白名单声明与答案形态不匹配，如 A3）/ **评测器层**
  （空白名单 unknown 误报，如 A2）/ **Agent 真实缺陷**。前三层是"评测体系自身误报"，
  聚类视图显式剥离后剩余的才是 Agent 的真实失败率。
- **验证方式**：在 754 案例 + mock 失败行为语料上聚类，人工抽检各簇归因正确率；
  构造含已知"规则层误报"的混入集，验证归因能把它分出来。**待采集数字**：
  评测体系误报占比（预期显著非零——A2/A3 就是实例）、各簇人工抽检一致率。
- **面试叙事点**：这是两篇文章最有普适性的洞察——**"通过率下降"的第一反应不该是改
  Agent，而是先归因到数据/规则/评测器/Agent 哪一层**；我们有 A2、A3 两个亲手踩的
  真实误报案例作证。

### B6. explanation 收敛验证：修复效果的闭环度量

- **设计**：基于 N2 scorer 契约的 `explanation` 字段（每个评测器的人可读判定依据），
  构建可复跑的正则/结构检测规则（如 `forbidden=[^]]*delete_namespace`），
  在修复前后两个时间窗对比命中数，验证"修了有没有用"。
- **验证方式**：以 A2（tool-policy 误报修复）为样板：修复前窗口 vs 修复后窗口的
  `unknown=\[` 命中数对比。**待采集数字**：命中数 before/after、整体失败数变化、
  与逐 run 复核的一致性。
- **面试叙事点**：结构化 explanation 不是给人看的装饰——它是**可查询的失败证据库**，
  让"修复验证"从重新跑全量回归降维到一次 SQL/正则统计。

## C. 通用验证方法设计（评测基础设施的可验证性，数字待回填）

> 评测工具与业务项目最大的不同：**测试床是自己生成的，ground truth 在构造时就已知**。
> 以下每个实验都能产出真实的 before/after 数字，且互为证据（A2/A3 的翻车就是 C7 要
> 自动拦截的对象）。

### C1. 诊断引擎标定（`diagnose-calibrate`）——构造即真值 ✅ 已完成（2026-10-18）

- **设计**：mock 每种失败行为在生成时就携带"预期诊断"标签。新命令跑 11 case 确定性
  语料 × 诊断引擎，输出混淆矩阵与 per-layer P/R/F1（`DiagnosisCalibration`，CLI 模块；
  eval 保持 adapter-free）；`--disable-rule A,B` 支持单规则消融（`DiagnosisEngine(Set)`）。
- **实测数字（首跑）**：11/11 全对、0 假阳性、四层 P=R=1.000；消融禁用
  unknownToolCalls+forbiddenToolCalls → 精确 4 个 MISS（7/11）且零假阳性——
  **每条规则的贡献第一次变成可量化数字**。
- **抓到的真实缺陷**：`giveUp()` 实现存在但未接进行为 switch——`agentBehavior:
  give_up` 静默落 default 生成 correct trace。标定首跑即抓出孤立分支并接线
  （ROADMAP 7.24）。
- **盲区被测量证实**：wrong_conclusion / fabricated_evidence / partial_evidence
  零诊断；cheat_tamper / cheat_hardcode 仅 tool_selection 间接信号——"答案-证据
  矛盾"与"篡改语义"无 trace 级规则，盲区清单成为后续规则设计的输入。
- **面试叙事点**：标签免费（确定性生成）；"标定不是证明引擎全对，而是把盲区从
  感觉变成数字"；首跑抓到死分支证明标定有真实检出力。

### C2. 回归门禁功效分析（gate power analysis）✅ 已完成（2026-10-18）

- **设计**：`gate-power` 命令构造已知质量差的版本对（p∈{0.9}, delta=5pp, 20 场景），
  模拟穿过**真实产品路径**（PassK.summarizeRaw + RegressionGate，非平行模型），
  虚警率/检出率 × tolerance 网格输出。
- **实测数字（核心命题命中）**：默认 tolerance=0 虚警率 **49.9%**——理论预测 ≈50%
  （avgPassRate 严格比较在方差下几乎永不打平）。tol 网格 0→0.30：虚警 0.499→0.019，
  检出 0.858→0.122（5pp 已是噪声地板）。**容忍定标经验**：pass^k 项 summary 级方差
  σ≈√(q(1-q)/S)（q=p^k）比 avg 项大 3 倍，容忍按 2-3 个 summary 级 σ 定。
- **配套落地**：RegressionGate 容忍语义同时约束两项（0.0 保持旧行为）、
  `compare --gate-tolerance` flag、compare 报告加 bootstrap CI + 精确 McNemar
  （实测 flaky 退化：delta=-0.45，CI 不跨 0，19 翻转 p≈0）。
- **面试叙事点**："你们的门禁能过吗"→"同质量版本对有 50% 概率虚警"——
  用蒙特卡洛穿过真实代码路径量化再修；功效/显著性框架在 CI 工程的完整移植。

### C3. FLAKY 分层的小样本误判率（给 `--repeats` 的统计指导）✅ 已完成（2026-10-18）

- **设计**：已知通过率 p 的模拟场景，repeats=k ∈ {2,3,5,10,20}，蒙特卡洛测
  STABLE_PASS / FLAKY / STABLE_FAIL 误判率矩阵；产出"区分 p=0.5 与 p=0.9 到 95% 置信
  所需最小 k"的指导表，写进 `run --repeats` 文档。
- **验证方式**：**解析解与蒙特卡洛对拍**——k 次全过/全败概率 = p^k+(1-p)^k，p=0.6、k=5
  时误判为稳定层的解析值 ≈ 8.8%，模拟结果必须落在其置信区间内。
- **实测数字**：200k 次/组 × 45 组（p∈{0.1..0.9}×k∈{2,3,5,10,20}），全部落在 4σ 内、
  最大偏差 <0.5pp；指导表 K=6(p=0.5)/14(0.8)/29(0.9)/59(0.95)，数字由
  `minRepeats(p,0.05)` 求出并在测试锚定（文档不可能与实现漂移）。
- **面试叙事点**：一个文档参数建议背后有解析推导+模拟验证双重支撑；
  "repeats=5 时 60% 通过率的场景约 9% 概率被误标为稳定层""90% 通过率的场景
  5 次重复只有 59% 概率被判稳定通过"这种数字面试官记得住。

### C4. PassK 归约器的性质测试 + 蒙特卡洛对拍 ✅ 已完成（2026-10-18）

- **设计**：(a) 数学序性质 pass^k ≤ pass@k ≤ avgPassRate（随机输入 1000 组零违例）；
  (b) 小 k 暴力枚举对拍；(c) 恒定 p 场景的闭式解 pass^k=p^k，蒙特卡洛 10k 次收敛验证。
- **实测数字**：序性质修正为准确形式 **pass^k ≤ passRate ≤ pass@k**（单场景 0/1 判定
  与比例的混合序，1000 组随机输入零违例）；穷举 k≤3 全部 2^k 输出形态，`aggregate()`
  与 `summarizeRaw()` 两条计算路径逐 case 等价 + at-least-m 边界（m=k≡pass^k、
  m=1≡pass@k）全对；闭式解 200k 次×6 组（p∈{0.3,0.7,0.9}×k∈{3,5}）全部 4σ 内收敛。
- **面试叙事点**：发布门禁的核心指标配数学级验证；property-based testing 方法论；
  "写性质测试时把序写反，穷举立刻抓出来"——对拍本身也验证了验证代码。

### C5. OTLP 映射的确定性与黄金文件

- **设计**：Event→Span 映射同输入跑两遍**字节级相同**；代表性 trace 的 golden OTLP
  JSON 进仓库 CI 对拍防漂移；runId→traceId 派生做 10 万级碰撞测试。
- **待采集数字**：字节差异 0；golden 对拍通过；碰撞 0/100k。
- **面试叙事点**："确定性"不是形容词，是可测性质；黄金文件是导出格式回归的最低成本护栏。

### C6. 存储与导入的往返/幂等/崩溃恢复性质

- **设计**：全 record 类型 save→load 逐字段相等；同一 session 导入两遍 → 第二遍
  RunExists 跳过、零重复行；写入中途 kill 进程 → WAL 恢复、库可打开、已完成 run 不丢。
- **待采集数字**：往返差异 0；重复行 0；中断注入后可打开率 100%。
- **面试叙事点**：评测工具卖点是"证据链完整"，证据链自身的完整性同样要工程验证
  （SQLite WAL 崩溃语义 + 幂等导入）。

### C7. 语料可判定性静态检查（corpus lint）——A3 教训的机制化

- **设计**：ScenarioLoader 落盘验证升级为 lint：`success_assertions` 每条声明做可满足性
  启发检查（contains 语序敏感 → 检查声明实词序列能否在场景根因/描述字段的合理语序中
  命中）、forbidden∩allowed 非空、k-of 的 k≤n 等结构检查；**754 案例全量跑 lint 出可疑清单**。
- **待采集数字**：lint 命中数、人工复核后的真实误配率、对 A3 类语序问题的召回。
- **面试叙事点**：质量体系的复利法则——**每个人工发现的翻车都要问"能不能变成落盘时
  自动拦截"**；A3 是活的输入案例。

### C8. 失败注入鲁棒性矩阵（fuzz-lite）

- **设计**：对统一 Trace 做变异（事件乱序 / 时间戳漂移 / 截断 / 空 attributes /
  非法枚举），评测+诊断链路对每组变异的行为三分类：崩溃（必须 0）/ 响亮失败（可接受）/
  **静默错误结果（必须 0——要害）**。
- **待采集数字**：变异用例数、崩溃数、静默错判数、响亮失败占比。
- **面试叙事点**：错报比崩溃危险（外部实践同款结论"稳定地判错比不稳定更危险"）；
  评测基础设施的鲁棒性标准是"永不静默错"。
